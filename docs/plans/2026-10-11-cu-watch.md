# `cu-watch`: a ClickUp comment watcher mod

The ask was a second mod for `sk-skills`, picked for the most value from real session history. The history scan (299 prompts in `~/.claude/history.jsonl`, 73 transcripts) found "check latest from sean in thread" typed 8 times and `/task <clickup url>` 7 times, all in the perch repos. Each check costs a full Claude turn plus MCP calls, and a reply that lands between checks goes unseen until the next ask. `cu-watch` turns that pull into a push: it watches the ClickUp task named by the current branch and tells Sam when someone comments.

It lives in `sk-skills` rather than `perch.martech`. `sk-skills` already holds the mod convention (`hooks/<mod>/register.tsx`, tests, `$.state` types) and `repo-status` already parses the `cu-<id>` out of the branch. `perch.martech` has commands, skills and a settings hook but no plugin or mod layout, so building it there would start a second convention. Every perch-specific value is configuration, not code, and the mod draws nothing outside a branch that carries a ClickUp ID, which in practice means only the perch repos (96 `cu-` branches in `perch.martech`, 57 in `modern-martech`, none elsewhere).

## Research findings

Verified:

- **The listener already covers autonomous sessions.** `perch.martech/docs/autonomous-sessions.md`: when Sam or Sean replies on a task, "the listener routes it back to you, so you do not need to poll". Autonomous sessions are the ones with `CLICKUP_AI_BOT_TOKEN` set. The gap is Sam's manual sessions, which is where all 8 "check latest" prompts came from.
- **ClickUp task comments.** `GET https://api.clickup.com/api/v2/task/{task_id}/comment` returns the 25 newest comments, newest first, each with `id`, `comment_text`, `user.id`, `user.username` and `date` (a millisecond timestamp as a string). Older pages take `start` plus `start_id`. Auth is the raw personal token in `Authorization`, as the perch `clickup-comment-as-ai-bot` skill already does with `curl`.
- **Perch identities.** Sean is ClickUp user `75368893`. AI Bot is `106444580`, and the listener already filters that actor out of its own event stream. Sam's personal token lives at `~/.clickup-perch-token`.
- **Mods API.** `$.clock.every` runs between turns without starting one. `$.http.fetch` returns `{ status, ok, headers, text }` with a 30-second cap. `$.ui.toast`, `$.ui.open` and a `Pane` render site are available on terminal and desktop. `$.prompt.submit({ text })` waits for the session to be idle and then starts a turn that names the mod as the sender. Commands registered with `immediate: true` run while Claude works. `$.store` is shared by every session on the machine, and per-key writes don't clobber each other.

Not yet verified (resolve in the first task, before building on them):

- **Threaded replies.** The task-comment endpoint's docs say `reply_count` is always 0 for threaded comments and document no reply endpoint. The ClickUp MCP exposes `clickup_get_threaded_comments`, which suggests one exists (likely `GET /comment/{comment_id}/reply`). A reply inside a thread may not show up in the task-comment list at all, and "latest from sean in thread" may mean exactly that.
- **Reading the token file.** Whether `$.fs.read` accepts an absolute path outside the session's working directory. `~` won't expand, so the path is built from `$.env.get('HOME')`.

## Resolved design

### Activation: branch ID, a token, and a manual session

The mod is live only when all three hold: the branch carries a `cu-<id>` (parsed with `repo-status`'s `parseStatus`, imported from `../repo-status/parse`), the configured token file reads, and `CLICKUP_AI_BOT_TOKEN` is unset. Otherwise it registers its command and stays silent.

_Why:_ the branch is the only place the task ID lives, and `repo-status` already reads it. The `CLICKUP_AI_BOT_TOKEN` check keeps it out of the listener's autonomous sessions, where a second notifier would double every reply.

### Configuration through `userConfig`

| Option | Perch value | Default |
| --- | --- | --- |
| `tokenFile` | `~/.clickup-perch-token` | unset, so the mod stays off |
| `ignoreUserIds` | `106444580` (AI Bot) | empty |
| `highlightUserIds` | `75368893` (Sean) | empty |
| `pollSeconds` | `120` | `120` |

Set once in `~/.claude/settings.json` under `pluginConfigs["sk-skills@sammykumar"]`. The token owner's own comments are always ignored: the first poll calls `GET /user` and records that ID.

_Why:_ a path rather than the token keeps the secret out of settings, and the same file the perch skill already uses means no new credential. Defaulting to off means installing `sk-skills` never starts polling for someone who hasn't set it up.

### Polling and what counts as new

Every `pollSeconds`, fetch the newest page for the branch's task. The high-water mark is the newest comment's `date` and `id`, kept in `$.store` under `seen:<taskId>`. The first poll for a task only records the mark, so old comments never toast. Every later poll treats comments past the mark, minus ignored and self-authored ones, as unread. It re-reads the mark from the store right before writing it, so two sessions on the same task don't both toast the same comment.

_Why:_ a key per task means sessions on different tasks never race. Re-reading before writing narrows the same-task race to a window of a few milliseconds. A missed notification there is cheap, because the pane still shows the comment.

### What Sam sees

- **Toast** for each new comment: `Sean on 86bbvedrf: <first 80 characters>`.
- **A band row** above the prompt while anything is unread: `💬 2 new on 86bbvedrf · /cu`, drawn beside `repo-status` by putting `await next(e)` among its children.
- **`/cu`** (registered `immediate: true`) opens a pane with the task name and status, then the last five comments: author, a 12-hour time, and the text. Comments from `highlightUserIds` are bold. Buttons: `[s] send to Claude` submits the newest unread comment through `$.prompt.submit`, framed as "Sean commented on ClickUp task 86bbvedrf: …". `[m] mark read` clears the band row. A `Link` opens the task in ClickUp. Opening the pane also marks everything read.
- **Phone:** the pane opens automatically on `session.attach` from `mobile` while anything is unread, mirroring `repo-status`.

_Why:_ the toast and band make it a push. Send-to-Claude stays a button and never fires automatically: in a manual session Sam decides what reaches Claude, the same rule the listener follows only because nobody is there to decide.

### Read-only toward ClickUp

The mod only issues `GET`s. No comments, status changes or reactions.

_Why:_ ClickUp is a client-visible third-party system, and Sam's standing rule is read-only by default there. Writing stays with the perch skill and its approval gate.

### Failure handling

A non-2xx response or a timeout sets a dim `cu-watch: ClickUp unreachable (401)` band row instead of failing silently, and retries at the next interval. A 401 also stops polling until the next session, so a revoked token doesn't produce a stream of failures.

## What was deliberately not built

- **Reading the listener's event stream** in place of polling. Less duplicate traffic, but it couples a general plugin to one repo's daemon. Revisit only if polling hits ClickUp rate limits.
- **Automatic send-to-Claude.** See above.
- **Watching tasks other than the branch's.** The `/task` workflow ties a session to one task, so the branch is the right scope for v1.
